# マスタメンテナンス画面 設計方針（新規システム向け）

> 対象例: 部署一覧画面（各行を入力し、右上の保存ボタン1つですべての行をcreate/updateする画面）
> 命名・アーキテクチャの詳細版は `マスタメンテナンスReact_SPA化設計方針.md` を参照。本ドキュメントは設計判断の経緯・比較検討のまとめ。

## 1. ルーティング・コントローラーメソッド命名

一覧の全行をまとめて保存する操作は「保存（Save）」であり、単一行のupdateとは性質が異なる。

- **ルーティング名**: `save`（スネークケース。Laravelのデフォルトルート名の慣習に合わせる）
- **コントローラーメソッド名**: `save`（PHPの慣習であるキャメルケース）

```php
Route::post('/departments/save', [DepartmentApiController::class, 'save'])
    ->name('departments.save');
```

### 命名バリエーション比較

| 案 | メリット | デメリット |
|---|---|---|
| `save`（採用） | create/update両対応の曖昧さを吸収。「保存」ボタン1つで全部保存するUIの実態と自然に対応 | 「何を保存するか」が名前だけでは不明瞭（ただしURL/コントローラーの文脈で十分補える） |
| `bulkUpdate` / `bulk_update` | 「複数まとめて」が最も直感的 | createも含むので若干語弊 |
| `batchUpdate` / `batch_update` | バッチ処理という文脈で自然 | 非同期処理と誤解されやすい |
| `sync` | 「一覧の状態に同期する」という意味合いが強い（削除も扱うなら特に適切） | createのみ/updateのみの場合はやや大げさ |

行の削除も将来的に一括画面でやる可能性があるなら`sync`、create/updateだけに閉じるなら`save`で確定。

UseCase層での振り分けイメージ:

```php
namespace App\UseCase\Master\Department;

class SaveUseCase
{
    public function execute(SaveInput $input): void
    {
        foreach ($input->rows as $row) {
            if ($row->id !== null) {
                $this->update($row);
            } else {
                $this->create($row);
            }
        }
    }
}
```

## 2. langファイル設計（FE表示）

### ファイル分割方針

画面・機能単位で分割し、共通要素は別出し。

```
lang/ja/departments.php    # 部署一覧・編集画面
lang/ja/employees.php      # 従業員関連画面
lang/ja/common.php         # save, cancel, delete, back など画面横断のボタン名
lang/ja/validation.php     # Laravel標準のバリデーションメッセージ
```

### キー命名パターン

```php
// lang/ja/common.php
return [
    'button' => [
        'save' => '保存',
        'cancel' => 'キャンセル',
        'delete' => '削除',
        'back' => '戻る',
        'confirm' => '確認',
        'search' => '検索',
    ],
];
```

```php
// lang/ja/departments.php
return [
    'title' => [
        'index' => '部署一覧',
        'edit' => '部署編集',
    ],
    'label' => [
        'name' => '部署名',
        'representative' => '代表者名',
    ],
    'message' => [
        'save_success' => '部署情報を更新しました',
        'save_confirm' => 'すべての変更を保存しますか？',
    ],
];
```

| 分類 | 命名例 | 補足 |
|---|---|---|
| ボタン | `button.save`, `button.delete` | 動詞そのまま。画面名を含めない（使い回すため） |
| ラベル | `label.name`, `label.status` | 名詞。DBカラム名に寄せると迷わない |
| タイトル | `title.index`, `title.edit` | 画面アクション名と揃える |
| メッセージ | `message.save_success`, `message.delete_confirm` | `動詞_success` / `動詞_confirm` / `動詞_error` で統一 |

- キーはDBカラム名やコントローラーメソッド名に寄せる
- ボタン名は極力`common`に集約し、画面ごとに再定義しない
- ネストは2階層まで

### 「〜を追加」など構造が共通で対象語だけ変わるボタン名

2つの方針を比較した結果、**個別キー方式を推奨**。

```php
// 方針B（推奨）: 対象ごとに個別キー
'button' => [
    'add_affiliation' => '所属を追加',
    'add_permission' => '権限を追加',
],
```

パラメータ化（`:attributeを追加`形式）も可能だが、Blade側の呼び出しが冗長になり可読性が落ちるため、対象が数個程度の場合は個別キーの方がバランスが良い。対象が10種類以上に及ぶ場合はパラメータ化を検討。

## 3. アーキテクチャ（Request → InputData → UseCase）

### 全体の流れ

```
Controller
  ↓ (FormRequestでバリデーション)
FormRequest (validated()でバリデーション済みデータ取得)
  ↓
InputData (DTO: UseCaseが必要とする形に整形)
  ↓
UseCase (ビジネスロジック実行)
  ↓
Response
```

### 実装例

```php
// FormRequest
namespace App\Http\Requests\Master\Department;

class SaveRequest extends FormRequest
{
    public function rules(): array
    {
        return [
            'departments' => ['required', 'array'],
            'departments.*.id' => ['nullable', 'integer'],
            'departments.*.name' => ['required', 'string', 'max:255'],
            'departments.*.representative_name' => ['required', 'string', 'max:255'],
        ];
    }
}
```

```php
// InputData（1行分）
namespace App\UseCase\Master\Department\Input;

final class RowInput
{
    public function __construct(
        public readonly ?int $id,
        public readonly string $name,
        public readonly string $representative_name,
    ) {
    }

    public static function fromArray(array $validated): self
    {
        return new self(
            id: $validated['id'] ?? null,
            name: $validated['name'],
            representative_name: $validated['representative_name'],
        );
    }
}
```

一覧全行をまとめて保存する場合はInputDataが配列を内包する:

```php
namespace App\UseCase\Master\Department\Input;

final class SaveInput
{
    /** @param RowInput[] $rows */
    public function __construct(
        public readonly array $rows,
    ) {
    }

    public static function fromArray(array $validated): self
    {
        return new self(
            rows: array_map(
                fn (array $row) => RowInput::fromArray($row),
                $validated['departments'],
            ),
        );
    }
}
```

## 4. UseCaseクラスの分割方針

**結論: アクションごとにUseCaseクラスを分割し、メソッド名は`execute()`に統一する。**

### 1つのUseCaseに複数アクションをまとめる場合の問題

- 単一責任の原則に反する（「一覧を見る」と「保存する」は別のユースケース）
- 依存が肥大化する（コンストラクタの依存関係が増え続ける）
- テストが書きにくい（1テストクラスにモック準備が混在）
- 複数メソッドがあると`execute()`という名前の意味がなくなる

### 推奨構成

UseCaseはリソースごとのディレクトリ配下に置くため、クラス名自体に対象リソース名（`Department`）を含めない。

```
app/UseCase/Master/Department/
    ListUseCase.php       // execute(): array
    SaveUseCase.php        // execute(SaveInput $input): void
    DeleteUseCase.php     // execute(int $id): void
    Input/
        SaveInput.php
        RowInput.php
```

```php
namespace App\UseCase\Master\Department;

class ListUseCase
{
    public function __construct(
        private DepartmentRepositoryInterface $department_repository,
    ) {
    }

    public function execute(): array
    {
        return $this->department_repository->findAll();
    }
}
```

| 観点 | 分割する場合 |
|---|---|
| 命名 | 全部`execute()`で統一できる（ディレクトリ＋クラス名で用途が分かる） |
| テスト | UseCase単位でテストクラスが1対1になり見通しが良い |
| 依存関係 | 各UseCaseが必要な依存だけを持てる |
| 変更の影響範囲 | `save`のロジック変更が`index`に影響しない |

## 5. コントローラーの分割方針

**結論: コントローラーはリソース単位でまとめたままでよい。UseCaseのように分割する必要はない。**

UseCase分割の理由は「ビジネスロジックの単一責任」だが、コントローラーはHTTPリクエストを受けて対応するUseCaseに委譲するだけで、ロジックをほぼ持たないため肥大化の心配がUseCaseほど深刻ではない。コントローラーは複数機能で横並びに識別する必要があるため、クラス名に`Department`を残す。

```php
namespace App\Http\Controllers\Api\Master;

use App\UseCase\Master\Department\ListUseCase;
use App\UseCase\Master\Department\SaveUseCase;
use App\UseCase\Master\Department\DeleteUseCase;
use App\UseCase\Master\Department\Input\SaveInput;
use App\Http\Requests\Master\Department\SaveRequest;

class DepartmentApiController extends Controller
{
    public function __construct(
        private ListUseCase $list_use_case,
        private SaveUseCase $save_use_case,
        private DeleteUseCase $delete_use_case,
    ) {
    }

    public function index()
    {
        $departments = $this->list_use_case->execute();

        return response()->json(['data' => $departments]);
    }

    public function save(SaveRequest $request)
    {
        $input = SaveInput::fromArray($request->validated());
        $this->save_use_case->execute($input);

        return response()->json([
            'message' => __('departments.message.save_success'),
        ]);
    }

    public function destroy(int $id)
    {
        $this->delete_use_case->execute($id);

        return response()->json(null, 204);
    }
}
```

### シングルアクションコントローラーが向くケース

- リソースに対応しない単発の操作（CSVエクスポート、一括承認バッチのトリガーなど）
- その操作だけが特別に複雑で、他のアクションと混ざると読みにくくなる場合
- UseCase＝コントローラーがほぼ1:1で、コンストラクタに1つのUseCaseだけを注入したい場合

### 判断の目安

| 状況 | 推奨 |
|---|---|
| 一般的なマスタメンテナンス（index/save/destroyなど、CRUD系がまとまっている） | **リソースコントローラーのまま**（分けない） |
| 特定のアクションだけが極端に複雑、または他のCRUDと文脈が違う | そのアクションだけシングルアクションコントローラーに切り出す |
| プロジェクト全体でシングルアクション統一という強いポリシーがある | 全部シングルアクションに揃える |

## 6. リポジトリ設計（Doctrine ORM使用時）

### EntityManagerInterfaceを直接DIする場合

```php
class DepartmentApiController extends Controller
{
    public function __construct(
        private EntityManagerInterface $entity_manager,
    ) {
    }
}
```

**メリット**
- 柔軟性が高い（`getRepository()`で任意のエンティティを取得可能）
- クエリビルダやDQLを直接書ける
- バインディング定義が不要
- トランザクション制御がしやすい

**デメリット**
- 責務が漏れやすい（クエリロジックがコントローラーに染み出す）
- テストがしにくい（`getRepository()`の戻り値までモックする必要がある）
- 再利用性が低い（同じクエリを複数箇所で重複させやすい）
- 抽象化レベルの不一致（ORM固有の概念が上位層に露出する）

### リポジトリ + インターフェース経由

```php
namespace App\Repository\Department;

interface DepartmentRepositoryInterface
{
    /** @return Department[] */
    public function findAll(): array;

    public function find(int $id): ?Department;

    public function save(Department $department): void;

    public function delete(Department $department): void;
}
```

```php
namespace App\Repository\Department;

use Doctrine\ORM\EntityRepository;

class DoctrineDepartmentRepository extends EntityRepository implements DepartmentRepositoryInterface
{
    public function findAll(): array
    {
        return $this->findBy([], ['name' => 'ASC']);
    }
}
```

**メリット**
- クエリロジックの置き場所が一元化される（重複排除）
- UseCase/コントローラーがクエリの詳細を知らずに済む
- テストで検索ロジックを差し替えられる（モック化しやすい）
- クエリが複雑化してもコード上の見た目の複雑さに直結しない

### 使い分けの目安

| 画面の特性 | 推奨 |
|---|---|
| 単純な`findAll()`, `find($id)`のみ | 直接DI/EntityManagerでも可 |
| 検索条件が2〜3個以上、動的にWHERE句が変わる | repository + interface |
| 複数テーブルJOIN、集計、ページネーション込み | repository + interface（必須級） |
| 同じ検索条件が複数のUseCase/画面から呼ばれる | repository + interface（重複排除の効果大） |

複雑なクエリが必要な画面では、検索条件をまとめる **Condition/Criteriaオブジェクト** を導入し、個別の`findByName()`, `findByStatus()`のようなメソッドを量産せず、条件オブジェクト1つを受け取る`search(Condition $condition)`に集約するのが良い。

### マスタメンテナンス（CRUDのみ）でもinterface経由でよいか

**結論: 問題ない。むしろ推奨。**

理由:
1. **一貫性が保てる** — 複雑な画面はinterface経由、単純なCRUDは直接DI、と混在させると判断コストが発生する
2. **将来複雑化する可能性がある** — マスタメンテナンスは運用が進むと検索条件が後から追加されがち。最初からinterface経由にしておけば実装差し替えの影響がコントローラー/UseCaseに及ばない
3. **オーバーヘッドは小さい** — CRUDのみなら`findAll()`, `find()`, `save()`, `delete()`程度で済み、複雑なCondition/Criteriaオブジェクトも不要

プロジェクト全体でUseCase層 + interface経由の設計を採用するなら、CRUDのみの画面も含めて統一するのがシンプル。

## 7. Entityの created_at / updated_at 自動設定（Doctrine ORM）

**結論: 共通トレイト + ライフサイクルコールバックで自動化する。**

DoctrineにはEloquentの`$timestamps = true`のような標準の自動タイムスタンプ機能がないため、`persist()`/`flush()`時に`created_at`/`updated_at`を自動設定する仕組みをEntity側に用意する必要がある。マスタメンテナンス対象のEntity数は20程度あるため、Entityごとに同じコードを重複させず、共通トレイトに集約する。

```php
namespace App\Entity\Concerns;

use Doctrine\ORM\Mapping as ORM;

trait TimestampableTrait
{
    #[ORM\Column(type: 'datetime')]
    protected \DateTimeImmutable $created_at;

    #[ORM\Column(type: 'datetime')]
    protected \DateTimeImmutable $updated_at;

    #[ORM\PrePersist]
    public function setCreatedAtOnPrePersist(): void
    {
        $this->created_at = new \DateTimeImmutable();
        $this->updated_at = new \DateTimeImmutable();
    }

    #[ORM\PreUpdate]
    public function setUpdatedAtOnPreUpdate(): void
    {
        $this->updated_at = new \DateTimeImmutable();
    }

    public function getCreatedAt(): \DateTimeImmutable
    {
        return $this->created_at;
    }

    public function getUpdatedAt(): \DateTimeImmutable
    {
        return $this->updated_at;
    }
}
```

各Entityは`use TimestampableTrait;`と`#[ORM\HasLifecycleCallbacks]`を付けるだけでよい。

```php
namespace App\Entity;

use App\Entity\Concerns\TimestampableTrait;
use Doctrine\ORM\Mapping as ORM;

#[ORM\Entity]
#[ORM\HasLifecycleCallbacks]
class Department
{
    use TimestampableTrait;

    // id, name, representative_name などの固有プロパティ
}
```

**注意点**
- `#[ORM\HasLifecycleCallbacks]`はEntity本体に付ける必要がある（トレイト側には付けられない）。付け忘れるとトレイトの`PrePersist`/`PreUpdate`が呼ばれず、`created_at`が未初期化のままflush()され、DoctrineのnotNullエラーになる
- 新規Entity作成時のチェック項目として、`use TimestampableTrait;`と`#[ORM\HasLifecycleCallbacks]`の付け忘れがないか確認する

## 8. コントローラーテストの書き方

CLAUDE.mdの規約（route()ヘルパー使用、actingAs()必須、create()でデータ準備、呼び出しメソッドはモック化、スネークケース変数名）に準拠。UseCaseをモック化してコントローラー単体のテストとする。

```php
<?php

namespace Tests\Http\Controllers\Api\Master;

use App\Models\User;
use App\UseCase\Master\Department\ListUseCase;
use Mockery;
use Tests\TestCase;

class DepartmentApiControllerTest extends TestCase
{
    public function test_部署一覧が取得できること()
    {
        $user = User::create([
            'name' => 'user_test',
            'email' => 'user_test@example.com',
            'password' => bcrypt('password'),
            'email_verified_at' => now(),
        ]);

        $mock_use_case = Mockery::mock(ListUseCase::class);
        $mock_use_case->shouldReceive('execute')
            ->once()
            ->andReturn([]);
        $this->app->instance(ListUseCase::class, $mock_use_case);

        $response = $this->actingAs($user)->get(route('api.master.departments.index'));

        $response->assertStatus(200);
        $response->assertJsonStructure(['data']);
    }

    public function test_未認証の場合401が返ること()
    {
        $response = $this->get(route('api.master.departments.index'));

        $response->assertStatus(401);
    }
}
```

ポイント:
- UseCaseをモック化し、`$this->app->instance()`でDIコンテナに差し替えを注入
- `route()`ヘルパーを使用
- `actingAs()`で認証済みユーザーとしてテスト（ユーザー種別は単一のため、ガード指定は不要）
- ユーザーは`create()`で直接作成（factory不使用）
- 変数名はスネークケース
- 未認証時のレスポンス確認も基本パターンとして追加（API化に伴い、Blade版の「ログイン画面へのリダイレクト」から「401」に変更）

## 9. Feature Test（View返却コントローラー・Doctrine環境）のテストDB管理

UseCase/Repositoryをモック化せず、実際にDBへ読み書きしてHTTPレスポンスやDBの状態を検証するFeature Testでは、テストDBのスキーマ管理とデータのクリーンアップに注意が必要。特にDoctrine ORM使用時はLaravel標準の`RefreshDatabase`だけでは事故が起きるため、専用の対応が要る。

`EntityManagerInterface`は`$this->app->make()`でDIコンテナから取得する。テストクラスごとに毎回書くと重複するため、共通基底クラス（`DoctrineTestCase`）にまとめておく。`Feature`/`Unit`どちらのテストからも使う可能性があるため、`tests/`直下に配置する。

### `RefreshDatabase`はDoctrine管理テーブルには使えない

**結論: Doctrineでテーブルを管理している場合、`RefreshDatabase`は使わない。**

`RefreshDatabase`はテストスイート初回実行時に内部で`migrate:fresh`相当の処理（全テーブルをdrop→Laravelのマイグレーションを再実行）を行う。この時Laravelの`php artisan migrate`が対象にするのは`database/migrations/`配下のマイグレーションのみで、Doctrineのマイグレーション（`doctrine:migrations:migrate`）やDoctrine Entityに対応するテーブルは対象外。

その結果、`RefreshDatabase`が全テーブルをdropした後、Laravel標準テーブル（`users`等）だけが再作成され、**Doctrine管理のテーブル（プロジェクトで作成した業務テーブル）は再作成されないまま消える**という事故が起きる。

### 推奨パターン: `DatabaseTransactions` + Doctrine側の明示的トランザクション

テストDBのスキーマ自体は事前に1回だけ（`migrate`と`doctrine:migrations:migrate`を両方）整えておき、各テストはテーブルのdrop/再作成を伴わない`DatabaseTransactions`トレイトと、Doctrine側の明示的なトランザクション開始・ロールバックを組み合わせて、データだけをクリーンに戻す。

```php
namespace Tests;

use Doctrine\ORM\EntityManagerInterface;
use Illuminate\Foundation\Testing\DatabaseTransactions;

class DoctrineTestCase extends TestCase
{
    use DatabaseTransactions;

    protected EntityManagerInterface $entity_manager;

    protected function setUp(): void
    {
        parent::setUp();

        $this->entity_manager = $this->app->make(EntityManagerInterface::class);
        $this->entity_manager->getConnection()->beginTransaction();
    }

    protected function tearDown(): void
    {
        $this->entity_manager->getConnection()->rollBack();
        $this->entity_manager->close();

        parent::tearDown();
    }
}
```

- `DatabaseTransactions`はEloquent側の接続にトランザクションを張るだけで、テーブルのdrop&再作成は一切行わない
- Doctrine側は`EntityManager`が独自のDBAL接続を持つため、Eloquent側のトランザクションに自動では乗らない。`getConnection()->beginTransaction()`/`rollBack()`で個別に制御する
- `rollBack()`後は`EntityManager`が閉じた状態になることがあるため、`close()`で明示的に閉じる

各Feature TestクラスはこのDoctrineTestCaseを継承する。

```php
namespace Tests\Feature\Controllers\Master;

use App\Entity\Department;
use Tests\DoctrineTestCase;

class DepartmentControllerTest extends DoctrineTestCase
{
    public function test_一覧画面が表示できる(): void
    {
        $department = new Department('経理部', '山田太郎');
        $this->entity_manager->persist($department);
        $this->entity_manager->flush();

        $response = $this->get(route('master.department.index'));

        $response->assertOk()
            ->assertViewIs('master.departments.index')
            ->assertViewHas('departments')
            ->assertSee('経理部');
    }
}
```

### テストDBの事前セットアップ（一度だけ）

`RefreshDatabase`を使わない前提のため、テストDBのスキーマは事前に手動またはCIのセットアップスクリプトで整えておく。

```bash
php artisan migrate --env=testing
php artisan doctrine:migrations:migrate --no-interaction
```

CI（GitHub Actions等）では、テストジョブの`php artisan migrate`ステップの後にDoctrineのマイグレーションコマンドも実行するステップを追加する。

### PHPStorm実行時の`.env.testing`が読まれない場合の注意

Docker Compose環境でPHPStormからテストを実行する際、`.env.testing`が用意されていても反映されないことがある。原因は多くの場合、PHPStorm側のテスト実行構成（Run/Debug Configurations）で`phpunit.xml`が明示的に指定されていないケース。

- `phpunit.xml`に`<env name="APP_ENV" value="testing" force="true"/>`を記載していても、実行構成の「Use alternative configuration file」が空欄だと、その`phpunit.xml`自体が使われず`APP_ENV`が反映されない
- 対策として実行構成に`phpunit.xml`のパス（コンテナ内パス）を明示的に指定する
- 併せてPHPStormのCLI Interpreterは「Docker Compose」で設定する（「Docker」単体だとdocker-compose.ymlのネットワーク定義に参加できず、DBのサービス名（例: `db`）が名前解決できずに接続エラーになる）
- 動作確認は`dump(env('APP_ENV'))`と`DB::connection()->getDatabaseName()`をテスト内に仕込んで、想定通りの環境・DBに接続されているか確認するとよい

### 命名ルールのまとめ

| 種別 | Department名を含めるか | 理由 |
|---|---|---|
| UseCase（`ListUseCase`, `SaveUseCase`, `DeleteUseCase`） | 含めない | `App\UseCase\Master\Department\`ディレクトリ配下にあり、既にリソースが特定されているため |
| InputData（`SaveInput`, `RowInput`） | 含めない | 同上（UseCaseと同じディレクトリ配下） |
| FormRequest（`SaveRequest`） | 含めない | 同上 |
| APIコントローラー（`DepartmentApiController`） | 含める | `Api/Master/`直下に機能ごとのコントローラーが横並びで置かれるため、ファイル名だけで識別する必要がある |
| Repositoryインターフェース／実装（`DepartmentRepositoryInterface`, `DoctrineDepartmentRepository`） | 含める | 同上（横並びで置かれる） |
| Reactのpage/hook/types | 含める | 機能ごとにディレクトリはあるが、コンポーネント名・フック名は単体でimportされるため名前で識別する必要がある |
