 開発環境の場合（データを消してよいなら、最もシンプル）

  php artisan doctrine:migrations:migrate first --no-interaction

  これで一旦マイグレーション0件の状態（全テーブル未作成）まで巻き戻し、その後：

  php artisan doctrine:migrations:migrate --no-interaction

  で1〜5番のマイグレーションを最初から実行し直します。ただし、この方法は巻き戻し時にdown()が正しく
  書かれている前提で、かつ既存の全データが消えます。

  特定のマイグレーションだけをやり直したい場合

  Doctrineマイグレーションは基本的に「順番に適用していく」設計なので、途中の1本だけを差し替えて再
  実行する標準的な方法はありません。もし2番のマイグレーションだけをやり直したいなら、以下の手順に
  なります。

  1.
  マイグレーション履歴テーブル（doctrine_migration_versions）から、2番以降のバージョン記録を削除
  2. t_doctorsを含む、2番以降で作られたテーブルを手動でDROP
  3. 2番のファイルを修正
  4. php artisan doctrine:migrations:migrateで再実行

⏺ RecordはTypeScriptの組み込みユーティリティ型で、「特定のキーの集合」と「値の型」を指定してオブジェクト型を作るためのものです。Button.tsxの実例で解説します。

  該当コードの再確認

  type Variant = 'primary' | 'secondary' | 'danger'

  const variantClasses: Record<Variant, string> = {
    primary: 'bg-slate-900 text-white hover:bg-slate-700',
    secondary: 'bg-white text-slate-700 border border-slate-300 hover:bg-slate-50',
    danger: 'bg-white text-red-600 border border-red-200 hover:bg-red-50',
  }

  Record<K, V>の基本

  Record<K, V>は「キーの型がK、値の型がVであるオブジェクト型」を意味します。

  Record<Variant, string>

  これは以下の型を書いたのと全く同じ意味になります。

  {
    primary: string
    secondary: string
    danger: string
  }

  Variantが'primary' | 'secondary' | 'danger'というユニオン型（前回説明した「リテラル型のユニオン」）なので、Record<Variant, string>は「primary, secondary,
  dangerという3つのキーを必ず全部持ち、それぞれの値がstring型である」というオブジェクトの型になります。

  なぜこう書くと便利か

  1. キーの網羅性がコンパイル時にチェックされる

  もしvariantClassesの中身からdangerを書き忘れたとします。

  const variantClasses: Record<Variant, string> = {
    primary: 'bg-slate-900 text-white hover:bg-slate-700',
    secondary: 'bg-white text-slate-700 border border-slate-300 hover:bg-slate-50',
    // dangerを書き忘れた
  }

  この場合、TypeScriptはコンパイルエラーを出します。「Variant型は3つの値を持つはずなのに、dangerのプロパティが足りない」と教えてくれます。これにより、Variant（Button.
  tsx側のtype Variant = 'primary' | 'secondary' | 'danger'）に新しい種類（例えば'warning'）を追加した際、対応するvariantClassesの定義を書き忘れることを防げます。

  2. 存在しないキーへのアクセスも防げる

  variantClasses['success']  // エラー：'success'はVariant型に存在しないキー

  もしsuccessのようなタイプミスや、まだVariantに追加していないキーでアクセスしようとすると、これもコンパイル時に検知されます。

  実際の使われ方（Button.tsx内）

  export function Button({
    variant = 'primary',
    className = '',
    ...props
  }: Props) {
    return (
      <button
        className={`... ${variantClasses[variant]} ${className}`}
        {...props}
      />
    )
  }

  variantClasses[variant]で、渡されたvariant（'primary', 'secondary',
  'danger'のいずれか）に対応するTailwindクラス文字列を取り出しています。variantの型がVariantで、variantClassesの型がRecord<Variant,
  string>なので、TypeScriptは「variantClasses[variant]は必ずstring型の値が返ってくる」と保証できます（undefinedになる可能性を考慮する必要がない）。

  Recordを使わずに書いた場合との比較

  もしRecordを使わず、単純なオブジェクトリテラルの型推論に任せた場合：

  // Recordを使わない場合
  const variantClasses = {
    primary: 'bg-slate-900 text-white hover:bg-slate-700',
    secondary: 'bg-white text-slate-700 border border-slate-300 hover:bg-slate-50',
    danger: 'bg-white text-red-600 border border-red-200 hover:bg-red-50',
  }

  この書き方でも一見動きますが、「Variant型とvariantClassesのキーが一致しているか」をTypeScriptが積極的にチェックしてくれません。例えばVariantに'warning'を追加しても
  、variantClasses側を更新し忘れてもエラーになりません（variantClasses['warning']にアクセスした瞬間にundefinedが返り、実行時までバグに気づけない）。

  Record<Variant, string>と明示することで、「Variantの全パターンに対応する値を用意する」という制約をコンパイル時に強制できるのが最大のメリットです。

  Recordの一般的な用途

  Button.tsxのような「列挙値→対応する値のマッピング」以外にも、以下のような場面でよく使われます。

  // APIレスポンスのエラーメッセージ集約（前回のuseDepartments.tsで実際に使用）
  type FieldErrors = Record<string, string[]>

  これはuseDepartments.tsにも登場していました。string（任意のフィールド名、例:
  departments.0.name）をキーに、string[]（そのフィールドのエラーメッセージ配列）を値に持つオブジェクト、という意味です。この場合キーがVariantのような限定されたリテラ
  ル型ではなくstring（任意の文字列）なので、「どんなキーでもよいが、値の型は必ずstring[]」という緩やかな制約になります。

  まとめ

  ┌──────────────────────────┬──────────────────────────────────────────────────────────────────────────┐
  │          書き方          │                                   意味                                   │
  ├──────────────────────────┼──────────────────────────────────────────────────────────────────────────┤
  │ Record<Variant, string>  │ キーは'primary' | 'secondary' | 'danger'のいずれかに限定、値は必ずstring │
  ├──────────────────────────┼──────────────────────────────────────────────────────────────────────────┤
  │ Record<string, string[]> │ キーは任意の文字列、値は必ずstring[]                                     │
  └──────────────────────────┴──────────────────────────────────────────────────────────────────────────┘

  Record<K, V>は「オブジェクトのキーと値の型を一括で指定する」ためのユーティリティ型で、特に今回のようにユニオン型をキーにする場合、コンパイル時の網羅性チェックという
  強力なメリットを得られます。

final class SaveUserInput
{
    /** @param int[] $permission_ids */
    public function __construct(
        public readonly string $print_name,
        public readonly string $name,
        public readonly UserType $type,
        public readonly int $department_id,
        public readonly ?string $login_id,
        public readonly ?string $password,
        public readonly array $permission_ids,
    ) {
    }

    public static function fromArray(array $validated): self
    {
        return new self(
            print_name: $validated['print_name'],
            name: $validated['name'],
            type: UserType::from($validated['type']),
            department_id: $validated['department_id'],

            password: $validated['password'] ?? null,
            permission_ids: $validated['permission_ids'] ?? [],
        );
    }
}

class UpdateSortOrderUseCase
{
    public function __construct(
        private UserRepositoryInterface $user_repository,
    ) {
    }

    public function execute(UpdateSortOrderInput $input): void
    {
        $users = $this->user_repository->findByIds($input->ids);
        $users_by_id = [];

        foreach ($users as $user) {
            $users_by_id[$user->getId()] = $user;
        }

        foreach ($input->ids as $sort_order => $id) {
            $users_by_id[$id]->changeSortOrder($sort_order);
        }

        $this->user_repository->flush();
    }
}

class UpdateUserUseCase
{
    public function __construct(
        private UserRepositoryInterface $user_repository,
        private UserPermissionRepositoryInterface $user_permission_repository,
    ) {
    }

    public function execute(int $id, SaveUserInput $input): void
    {
        $user = $this->user_repository->find($id);

        if ($user === null) {
            throw NotFoundException::forId('ユーザー', $id);
        }

        $user->changePrintName($input->print_name);
        $user->changeName($input->name);
        $user->changeType($input->type);
        $user->changeDepartmentId($input->department_id);
        $user->changeLoginId($input->login_id);

        if ($input->password !== null && $input->password !== '') {
            $user->changePassword(Hash::make($input->password));
        }

        $this->user_repository->flush();

        $this->user_permission_repository->replaceForUser($id, $input->permission_ids);
    }
}

class SaveUserUseCase
{
    public function __construct(
        private UserRepositoryInterface $user_repository,
        private UserPermissionRepositoryInterface $user_permission_repository,
    ) {
    }

    public function execute(SaveUserInput $input): User
    {
        $sort_order = $this->user_repository->findMaxSortOrderByDepartmentAndType(
            $input->department_id,
            $input->type,
        );

        $user = new User(
            print_name: $input->print_name,
            name: $input->name,
            type: $input->type,
            department_id: $input->department_id,
            login_id: $input->login_id,
            password: $input->password === null ? null : Hash::make($input->password),
            sort_order: $sort_order === null ? 0 : $sort_order + 1,
        );

        $this->user_repository->save($user);
        $this->user_repository->flush();

        $this->user_permission_repository->replaceForUser($user->getId(), $input->permission_ids);

        return $user;
    }
}

            'department_id' => $user->getDepartmentId(),
            'login_id' => $user->getLoginId(),
            'permission_ids' => $this->user_permission_repository->findPermissionIdsByUserId($id),
        ];
    }
}

class HalfWidthAlphanumeric implements ValidationRule
{
    private const REGEX = '/^[a-zA-Z0-9]+$/';

    public function validate(string $attribute, mixed $value, Closure $fail): void
    {
        if (!is_string($value)) {
            return;
        }

        if (preg_match(self::REGEX, $value) !== 1) {
            $fail('validation.half_width_alphanumeric')->translate();
        }
    }
}

/**
 * 半角英数字とASCII印刷可能記号のみを許容するルール。
 */
class HalfWidthAlphanumericSymbol implements ValidationRule
{
    private const REGEX = '/^[a-zA-Z0-9!-\/:-@\[-`{-~]+$/';

    public function validate(string $attribute, mixed $value, Closure $fail): void
    {
        if (!is_string($value)) {
            return;
        }

        if (preg_match(self::REGEX, $value) !== 1) {
            $fail('validation.half_width_alphanumeric_symbol')->translate();
        }
    }
}

⏺ このフックには2段階の初期化フローがあります。

  fetchInitial + 1つ目のuseEffect（54〜83行目）

  役割：画面を開いた瞬間に一度だけ実行される「初期データ取得」

  useEffect(() => {
    fetchInitial()
  }, [fetchInitial])

  fetchInitialはuseCallbackで依存配列[]（空）なので、コンポーネントの生存期間中ずっと同じ関数の参照を保つ。つまりこのuseEffectは実質「マウント時に1回だけ
  」動く。

  中身は：
  1. 所属一覧（/api/master/departments）と権限一覧（/api/master/users/permissions）をPromise.allで並行取得
  2. 所属をsort_order昇順にソート
  3. departments・permissionsのstateにセット
  4. 取得した所属の先頭をselected_department_idに自動選択

  この「先頭の所属を自動選択する」処理（71〜73行目）が、2つ目のuseEffectを連鎖的に起動するトリガーになっている。

  fetchUsers + 2つ目のuseEffect（85〜107行目）

  役割：「どの所属・どの区分が選ばれているか」に応じてユーザー一覧を再取得する

  useEffect(() => {
    if (selected_department_id === null) {
      return
    }
    setDraftUsers([])
    fetchUsers(selected_department_id, selected_type)
  }, [selected_department_id, selected_type, fetchUsers])

  依存配列にselected_department_idとselected_typeが入っているので、以下のどのタイミングでも自動的に発火する：

  - 初回：fetchInitialが所属を自動選択した瞬間（selected_department_idがnull→数値に変わる）
  - ユーザーがchangeDepartmentで所属を切り替えたとき
  - ユーザーがchangeTypeで区分（スタッフ／外部スタッフ）を切り替えたとき

  selected_department_id === nullのガードは、初期状態（まだ所属が選ばれていない一瞬）でAPIを叩かないようにするため。setDraftUsers([])は、所属や区分を切り替え
  たら「追加中の未保存行」を破棄する意図（別の所属に切り替えたのに前の所属用の追加フォームが残っているのはおかしいため）。

  2つを合わせた全体の流れ

  マウント
    → fetchInitial実行（所属・権限取得）
        → selected_department_id が null → 先頭所属のIDに変化
            → 2つ目のuseEffectが依存配列の変化を検知して発火
                → fetchUsers実行（そのユーザー一覧を取得）

  「初期データ取得」と「選択条件に応じた一覧取得」を責務ごとに分離し、後者は選択条件が変わるたびに自動で再実行される設計になっている。useCallbackで両関数
  をメモ化しているのは、useEffectの依存配列に関数自体を含めても不要な再実行を起こさないようにするため（関数の参照が毎レンダーで変わるとuseEffectが無限ルー
  プしかねない）。

    fetchInitial()
  }, [fetchInitial])

  const fetchUsers = useCallback(async (department_id: number, type: UserType) => {
    setIsUsersLoading(true)
    setErrorMessage(null)

    try {
      const response = await axios.get<{ data: UserListItem[] }>('/api/master/users', {
        params: { department_id, type },
      })
      setUsers(response.data.data)
    } catch (error) {
      setErrorMessage('一覧の取得に失敗しました')
    } finally {
      setIsUsersLoading(false)
    }
  }, [])

  useEffect(() => {
    if (selected_department_id === null) {
      return
    }
    setDraftUsers([])
    fetchUsers(selected_department_id, selected_type)
  }, [selected_department_id, selected_type, fetchUsers])

  function changeDepartment(department_id: number) {
    setSelectedDepartmentId(department_id)
    setSelectedUserId(null)
    setForm(null)
  }

  function changeType(type: UserType) {
    setSelectedType(type)
    setSelectedUserId(null)
    setForm(null)
  }

  function addDraftUser() {
    const draft_id = draft_id_sequence--
    setDraftUsers((prev) => [...prev, { draft_id, type: selected_type }])
    setSelectedUserId(null)
    setForm(emptyForm(selected_department_id, selected_type))
    setFieldErrors({})
    setErrorMessage(null)
    setSuccessMessage(null)
  }

  async function selectUser(user_id: number) {
    setSelectedUserId(user_id)
    setForm(null)
    setFieldErrors({})
    setErrorMessage(null)
    setSuccessMessage(null)

    try {
      const response = await axios.get<{ data: UserDetail }>(`/api/master/users/${user_id}`)
      const detail = response.data.data
      setForm({
        print_name: detail.print_name,
        name: detail.name,
        type: detail.type,
        department_id: detail.department_id,
        login_id: detail.login_id,
        password: '',
        permission_ids: detail.permission_ids,
      })
    } catch (error) {
      setErrorMessage('ユーザー詳細の取得に失敗しました')
      setSelectedUserId(null)
    }
  }

  function updateForm<K extends keyof UserFormValues>(field: K, value: UserFormValues[K]) {
    setForm((prev) => (prev === null ? prev : { ...prev, [field]: value }))
  }

  function togglePermission(permission_id: number) {
    setForm((prev) => {
      if (prev === null) {
        return prev
      }
      const has = prev.permission_ids.includes(permission_id)
      return {
        ...prev,
        permission_ids: has
          ? prev.permission_ids.filter((id) => id !== permission_id)
          : [...prev.permission_ids, permission_id],
      }
    })
  }

  async function save() {
    if (form === null || form.department_id === null) {
      return
    }

    setIsSaving(true)
    setErrorMessage(null)
    setSuccessMessage(null)
    setFieldErrors({})

    const payload = {
      print_name: form.print_name,
      name: form.name,
      type: form.type,
      department_id: form.department_id,
      login_id: form.login_id,
      password: form.password === '' ? null : form.password,
      permission_ids: form.permission_ids,
    }

    try {
      if (selected_user_id === null) {
        const response = await axios.post<{ data: { id: number } }>(
          '/api/master/users/save',
          payload,
        )
        setDraftUsers([])
        setSelectedUserId(response.data.data.id)
      } else {
        await axios.put(`/api/master/users/${selected_user_id}`, payload)
      }

      if (selected_department_id !== null) {
        await fetchUsers(selected_department_id, selected_type)
      }

      setSuccessMessage('保存しました')
    } catch (error) {
      if (axios.isAxiosError(error) && error.response) {
        if (error.response.status === 422) {
          setFieldErrors(error.response.data.errors ?? {})
          setErrorMessage(error.response.data.message)
        } else {
          setErrorMessage(error.response.data.message ?? '保存に失敗しました')
        }
      } else {
        setErrorMessage('通信エラーが発生しました')
      }
    } finally {
      setIsSaving(false)
    }
  }

  async function reorderUsers(from_index: number, to_index: number) {
    if (from_index === to_index) {
      return
    }

    const reordered = [...users]
    const [moved] = reordered.splice(from_index, 1)
    reordered.splice(to_index, 0, moved)

    setUsers(reordered)
    setErrorMessage(null)

    try {
      await axios.put('/api/master/users/sort-order', {
        ids: reordered.map((row) => row.id),
      })
    } catch (error) {
      if (axios.isAxiosError(error) && error.response) {
        setErrorMessage(error.response.data.message ?? '表示順の更新に失敗しました')
      } else {
        setErrorMessage('通信エラーが発生しました')
      }
    }
  }

  async function destroyUser() {
    if (selected_user_id === null || form === null) {
      return
    }

    if (!window.confirm(`${form.name}を削除しますか？`)) {
      return
    }

    setErrorMessage(null)
    setSuccessMessage(null)

    try {
      await axios.delete(`/api/master/users/${selected_user_id}`)
      setSelectedUserId(null)
      setForm(null)

      if (selected_department_id !== null) {
        await fetchUsers(selected_department_id, selected_type)
      }
    } catch (error) {
      if (axios.isAxiosError(error) && error.response) {
        setErrorMessage(error.response.data.message ?? '削除に失敗しました')
      } else {
        setErrorMessage('通信エラーが発生しました')
      }
    }
  }

  function getFieldError(field: string): string | undefined {
    return field_errors[field]?.[0]
  }

  return {
    departments,
    permissions,
    selected_department_id,
    selected_type,
    users,
    draft_users,
    selected_user_id,
    form,
    is_loading,
    is_users_loading,
    is_saving,
    error_message,
    success_message,
    changeDepartment,
    changeType,
    addDraftUser,
    selectUser,
    updateForm,
    togglePermission,
    save,
    reorderUsers,
    destroyUser,
    getFieldError,
  }
}

  togglePermission関数

  function togglePermission(permission_id: number) {
    setForm((prev) => {
      if (prev === null) {
        return prev
      }
      const has = prev.permission_ids.includes(permission_id)
      return {
        ...prev,
        permission_ids: has
          ? prev.permission_ids.filter((id) => id !== permission_id)
          : [...prev.permission_ids, permission_id],
      }
    })
  }

  setFormに関数を渡している（setForm((prev) => ...)という形）。これは「更新関数（updater
  function）」と呼ばれるReactのパターンで、直前のstate（prev）を受け取って新しいstateを返す。

  処理の流れ：
  1. prev === nullガード：formはユーザー未選択時にnullになりうる型（UserFormValues |
  null）。フォームが開いていない状態でこの関数が呼ばれることは実際にはない（チェックボックス自体がform !==
  nullのときしか描画されない）が、型上prevはnullもありうるので、TypeScriptに「nullなら何もしない」と明示している
  2. has判定：今のpermission_ids配列にこのpermission_idが既に含まれているかを確認
  3. トグル：
    - 含まれている（has === true）→ filterでその要素を除いた新しい配列を作る（チェックを外す）
    - 含まれていない（has === false）→ スプレッドで既存配列の末尾に追加した新しい配列を作る（チェックを入れる）
  4. { ...prev, permission_ids: ... }で、permission_ids以外のフィールド（nameやlogin_idなど）はそのまま維持した新しいオブジェクトを返す

  なぜ更新関数の形（(prev) => ...）を使うか：setForm(form => ...)ではなくsetForm({...form, ...})のように直接クロージャ内のformを参照する書き方だと、短時間
  に連続でクリックされたときに古いformを参照してしまう可能性がある。更新関数なら常にReactが管理する最新のstateをprevとして渡してくれるので安全。

  なぜ新しい配列・オブジェクトを作るか（filterや[...prev.permission_ids,
  x]で元の配列を書き換えない）：Reactは参照が変わったかどうかでstateの変化を検知する。元の配列をpushやspliceで直接変更（ミューテーション）すると、配列の参
  照は同じままなのでReactが変化を検知できず再レンダリングされない。これがReactにおける「イミュータブルな更新」の基本ルール。

  チェックボックス側

  <input
    type="checkbox"
    checked={form.permission_ids.includes(permission.id)}
    onChange={() => togglePermission(permission.id)}
  />

  これは**制御コンポーネント（controlled component）**のパターン。

  - checked={...}：チェックボックスの見た目（オン/オフ）は、DOM自身の内部状態ではなく、常にReactのstate（form.permission_idsにその権限IDが含まれているか）
  から決まる。つまり「真実の情報源（source of truth）」はReact側にある
  - onChange：ユーザーがクリックしてチェック状態を変えようとした瞬間に発火し、togglePermissionを呼んでstateを更新する。stateが更新されると再レンダリングが
  走り、checkedの値が新しいpermission_idsに基づいて再計算される

  流れをまとめると：

  クリック
    → onChange発火 → togglePermission(id)
        → setForm(prev => 新しいpermission_ids配列を含むフォーム)
            → 再レンダリング
                → checked = form.permission_ids.includes(id) が再評価される
                    → チェックボックスの見た目が更新される

  DOMのチェックボックスを直接いじるのではなく、「stateを更新→Reactが見た目を再計算」という一方向のデータフローで動いている






let draft_id_sequence = -1

  役割：まだサーバーに保存されていない「新規追加中のユーザー」に、一時的な負のIDを振るためのカウンター。

  function addDraftUser() {
    const draft_id = draft_id_sequence--   // -1, -2, -3, ... と減っていく
    setDraftUsers((prev) => [...prev, { draft_id, type: selected_type }])
    ...
  }

  「スタッフ追加」ボタン（UserManagementPage.tsx:121）を押すたびにdraft_id_sequence--が呼ばれ、-1 → -2 →
  -3と一意な負の数を採番する。DBの実IDは正の整数なので、負の数を使うことで「これは未保存のダミーIDだ」と一目で区別できる。

  なぜモジュールスコープのlet（フック内のstateではない）なのか：
  - Reactのstateにすると再レンダリングのたびに値が巻き戻る恐れがあり、カウンターとしては不適切
  - 単なるインクリメント/デクリメントのカウンターは画面の再描画と無関係なただの値なので、モジュールスコープの変数で十分
  - ただし、複数のブラウザタブ/複数のuseUsers()呼び出し間で共有されてしまう点はトレードオフだが、ページは1つのユーザー管理画面インスタンスしか使わない前提
  なので実害はない

  UserFormValues型

  編集・新規作成どちらの場合にも使う、フォームの入力値をまとめた型。

  export type UserFormValues = {
    print_name: string
    name: string
    type: UserType
    department_id: number | null
    login_id: string
    password: string
    permission_ids: number[]
  }

  - department_idだけnumber |
  nullなのは、所属一覧の取得前など「まだ何も選ばれていない」状態がありうるため（emptyForm呼び出し元でselected_department_idがまだnullの可能性を考慮）
  - login_id/passwordはバックエンドではnullable（前回の変更）だが、フォーム上は常に文字列（空文字 =
  未入力）として扱う。送信時（save関数）で空文字をnullに変換している

  emptyForm関数

  新規追加フォームを開くときの初期値を作るファクトリ関数。

  function emptyForm(department_id: number | null, type: UserType): UserFormValues {
    return {
      print_name: '',
      name: '',
      type,
      department_id,
      login_id: '',
      password: '',
      permission_ids: [],
    }
  }

  呼び出し箇所（addDraftUser内）：
  setForm(emptyForm(selected_department_id, selected_type))

  現在選択中の所属・区分を初期値として引き継ぎつつ、他のフィールドは空にしたフォームを生成する。「今表示している所属・区分にユーザーを追加する」という自然な挙
  動を実現するため、department_idとtypeだけ引数で受け取っている。

  3つの関係性まとめ

  「スタッフ追加」ボタンを押すと：
  1. addDraftUser()が呼ばれる
  2. draft_id_sequenceをデクリメントして一時ID（例：-1）を発行
  3. 左のリストに{ draft_id: -1, type: selected_type }という表示専用のプレースホルダー（draft_users）を追加（「未入力」「ID未指定」と表示される行）
  4. 右側の編集フォームにはemptyForm(...)で空フォームをセット

  ユーザーが実際に保存（save関数）すると、サーバーからの応答で本物のIDが払い出され、draft_usersはクリアされてusers（本物の一覧）に置き換わる、という流れ。
  draft_id自体はサーバーには送信されず、あくまでReactのkeyとUI表示のためだけに使われる一時的な値。
